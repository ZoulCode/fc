المحاضرة 1: SDLC و Business Analysis

قبل ما تدخل لازم تعرف

  • SDLC (6 مراحل): Planning ← Analysis ← Design ← Implementation ← Testing ← Maintenance. المخرجات: software + documentation + training للمستخدمين.
  • Planning: لماذا نبني النظام (need) وكيف سنبنيه (plan). فيها Project Initiation (business need + Feasibility) ثم Project Management. المخرج: Project Plan.
  • Feasibility: Technical (نقدر نبنيه؟)، Economic (يعطي قيمة؟)، Organizational (لو بنيناه حيُستخدم؟). وفي الشرائح كمان: Operational وSchedule. هدفها تحديد المشكلة ونطاقها وليس حلها. مخرجها: system proposal.
  • Analysis: مين بيستخدم، النظام بيعمل إيه، وين ومتى. جزءين: Requirements Determination وRequirements Structuring.
  • Design: Logical design (الوظائف بغض النظر عن المنصة) ثم Physical design (تفاصيل تقنية).
  • Implementation: code، validate، install، support. Maintenance: مش مرحلة منفصلة، هي تكرار للمراحل الأخرى.
  • Business Analyst vs System Analyst: BA تركيزه على الـ business process وممكن يحل المشكلة من غير تغيير software. SA تقني، بيجي بس لما فيه software change (data modeling، تكامل الأنظمة).
  • مهارات System Analyst الست: technical, business, analytical, interpersonal, management, ethical.
  • Core Concept Model (6): Need, Change, Solution, Stakeholder, Value, Context.
  • Stakeholder roles: customer, end user, domain SME, implementation SME, project manager, operational support, regulator, sponsor, supplier, tester.
  • Value: Tangible (قابلة للقياس مباشرة، مالية) وIntangible (تقاس بشكل غير مباشر، زي سمعة الشركة وروح الموظفين).
  • CASE tools: diagramming، display/report generators، analysis tools (تفحص النواقص والتناقض)، central repository، documentation generators، code generators. أمثلة: Oracle Designer, Rational Rose, Eclipse.
  • Outsourcing: الأسباب: cost-effective، تحرير موارد داخلية، تقليل time-to-market، رفع كفاءة العمليات، تطوير النظم non-core.

فرّق بين Business Analyst وSystem Analyst.
BA: تركيز على الـ business process، قد يحل المشكلة دون تغيير في الـ software. SA: تركيز تقني، يتدخل فقط عند وجود software change ويهتم بـ data modeling وتدفق البيانات وتكامل الأنظمة.

Technical, Economic, Organizational/Operational, Schedule (اشرح كل واحد بجملة من فوق). المخرج: formal system proposal هو وثيقة قرار فيها طبيعة ونطاق النظام المقترح. هدفها تحديد outline المشكلة وscope وليس حلها.
ليه الـ Maintenance مش مرحلة منفصلة؟
لأنها تكرار للمراحل الأخرى (planning, analysis, design...) بتتعمل لإصلاح وتحسين النظام بشكل منتظم.
عدّد الـ 6 core concepts وعرّف اثنين منها.
Need: مشكلة أو فرصة يجب معالجتها. Change: فعل التحول استجابة لحاجة. Solution: طريقة محددة لإشباع حاجة في سياق. Stakeholder: فرد أو مجموعة لها علاقة بالتغيير أو الحاجة أو الحل. Value: أهمية الشيء لـ stakeholder في سياق. Context: الظروف المحيطة التي تؤثر في التغيير.

Logical: الخصائص الوظيفية مستقلة عن المنصة. Physical: تحويل المواصفات المنطقية إلى تفاصيل خاصة بالتقنية.

المحاضرة 2: Project Planning (Sommerville ch. 23)

قبل ما تدخل لازم تعرف

  • Planning stages (3): Proposal (لتسعير النظام)، Project startup (لتحديد من يعمل وكيف يقسم المشروع وتخصيص الموارد)، Development (تعديل الخطة دورياً بحسب الخبرة والمتابعة). حتى الـ agile يحتاج startup plan.
  • عوامل تسعير البرمجيات (5): Contractual terms, Cost estimate uncertainty, Financial health, Market opportunity, Requirements volatility.
  • Under pricing: للفوز بعقد يحتفظ بالموظفين، أو لدخول سوق جديد. Increased pricing: لما العميل يريد fixed-price فالمورد يرفع السعر لتغطية المخاطر غير المتوقعة.
  • Plan-driven: مع: تؤخذ القضايا التنظيمية بالحسبان ويتم اكتشاف المشاكل والـ dependencies قبل البدء. ضد: كثير من القرارات المبكرة يتم تعديلها بسبب تغير البيئة.
  • أقسام الـ project plan (7): Introduction, Project organization, Risk analysis, HW/SW resource requirements, Work breakdown, Project schedule, Monitoring & reporting.
  • الخطط الإضافية (5): Configuration management, Deployment, Maintenance, Quality, Validation.
  • افتراضات واقعية + contingency. لو حصلت مشاكل كبيرة: risk mitigation + re-plan + إعادة التفاوض على القيود والـ deliverables + جدول جديد يتفق عليه مع العميل.
  • Scheduling activities (4): تقسيم المشروع لمهام وتقدير الوقت والموارد؛ تنظيم المهام بالتوازي؛ تقليل الـ dependencies؛ تعتمد على حدس وخبرة المدير.
  • Scheduling problems (4): صعوبة تقدير الصعوبة والتكلفة؛ الإنتاجية لا تتناسب مع عدد الأشخاص؛ إضافة أشخاص لمشروع متأخر تؤخره (communication overhead)؛ غير المتوقع يحدث دائماً فاترك contingency.
  • كل activity لها: duration، effort (person-days)، deadline، defined end-point. المهام لازم تكون حوالي أسبوع أو أسبوعين.
  • Milestone = نقطة في الجدول لتقييم التقدم (مثل تسليم النظام للاختبار). Deliverable = منتج عمل يُسلّم للعميل (مثل requirements document).
  • أدوات العرض: Bar charts (calendar-based) وActivity networks (تُظهر الـ dependencies). أدوات: Basecamp, MS Project.
  • الـ Critical path: أطول مسار في الـ activity network، وهو يحدد أقل زمن لإنهاء المشروع.

مثال بناء البيت (مهم للحساب)

  • Most likely = مجموع الأزمنة المتوقعة على الـ critical path = 5+2+12+9+10+7+5 = 50 يوم.
  • Optimistic = 4+2+10+8+8+7+4 = 43. Pessimistic = 7+3+14+10+11+8+6 = 59.
  • الخلاصة: غالباً 50 يوم، ممكن تخلص في 43، وممكن توصل 59.
تنبيه على مثال T1–T12 الشريحة بتقول الـ critical path = 55 يوم. أنا لما حسبته من الجدول اللي في الشريحة (T1=10, T3=15, T9=15, T11=10, T12=10) طلع 60، والرسمة نفسها فيها أرقام مختلفة شوية (T1=8, T11=7). يعني فيه عدم اتساق في الشرائح. اسأل الدكتورة أو المعيد أي رقم معتمد. في الامتحان اعرض الطريقة (forward pass: كل مهمة تبدأ بعد انتهاء أكبر dependency) وحدد المسار بوضوح.

المحاضرة 3: Requirements

قبل ما تدخل لازم تعرف

  • Requirement = تمثيل قابل للاستخدام لـ need. يحدد: Feature (مثل Cloud Access)، Function (مثل Calculate Savings)، Fact يجب أن يفرضه الحل (لوائح)، Quality (مثل فتح الملف في ثانية).
  • التصنيف (4 أنواع):
    • Business: أهداف عليا، تجيب على "لماذا المشروع"، يحددها المستوى التنفيذي في BRD.
    • Stakeholder: احتياجات stakeholder وكيف يتفاعل مع الحل. الجسر بين business وsolution. "ما المطلوب" وليس "كيف".
    • Solution: خصائص الحل، وتنقسم إلى Functional وNon-functional.
    • Transition: قدرات مؤقتة لنقل الحل من as-is إلى to-be (data conversion، training، business continuity). غير مطلوبة بعد دخول الحل production. مثالها: "Sales personnel must attend 2-day program قبل استخدام النظام".
  • Functional: الخدمات التي ينبغي أن يقدمها النظام وكيف يتفاعل مع مدخلات معينة، وقد تذكر ما يجب ألا يفعله. Non-functional: قيود على الخدمات (زمن، عملية التطوير، معايير) وغالباً على النظام ككل.
  • 3Cs: Clear, Complete, Consistent. الغموض مثل كلمة "search" (المستخدم يقصد كل العيادات، المطور يفهمها عيادة واحدة).
  • أنواع الـ functional (9): Authentication، Authorization levels، Data processing، UI/UX، Reporting، System integration، Transaction handling، Error handling & logging، Backup & recovery.
  • Functional decomposition / WBS: High-level function ← Subfunction ← Process ← Activity، نفكك لحد ما ما يعود ينقسم.
  • Goal vs Verifiable NFR: "سهل الاستخدام" = goal لا يُختبر. "الطاقم يستخدم كل الوظائف بعد 4 ساعات تدريب وبمتوسط أخطاء لا يتجاوز 2 في الساعة" = verifiable.
  • تصنيف الـ NFR (3): Product (سرعة، reliability)، Organisational (سياسات وإجراءات المؤسسة)، External (تشريعات وinteroperability).
  • مقاييس NFR: Speed (transactions/second، response time)، Size (MB)، Ease of use (training time)، Reliability (MTTF، احتمال عدم التوفر)، Robustness (وقت إعادة التشغيل)، ...
  • FURPS: Functionality, Usability, Reliability, Performance, Supportability. FURPS+ تضيف: Design constraints, Implementation, Interface, Physical.
  • Perfect Technology: لو الـ requirement يبقى مطلوباً حتى مع تقنية مثالية = functional، وإلا = non-functional.
  • Elicitation tasks (4): Prepare, Conduct, Confirm results, Manage stakeholder collaboration.
  • Stakeholder collaboration: lists, maps, personas. Stakeholder matrix = influence مقابل impact. Persona = شخصية تمثيلية لفئة مستخدمين. Proto-persona = persona مبنية على معلومات محدودة (أفضل من لا شيء).

المحاضرة 4: Elicitation & Specification & Validation

قبل ما تدخل لازم تعرف

  • Elicitation techniques: Traditional (5): interviewing individuals، interviewing groups، survey/questionnaire، ethnography، analyzing procedures/documents. Modern (3): JAD، CASE tools، Prototyping.
  • Open-ended questions: مزايا: تظهر معلومات غير متوقعة، تريح المُقابَل، تعطيه إحساساً بالمشاركة. عيوب: تأخذ وقتاً، صعبة التلخيص.
  • Closed-ended: مزايا: مناسبة لما الإجابات معروفة، لا تأخذ وقتاً، بداية سهلة للمقابلة، ويمكن إضافة "other". عيب: قد تفوت معلومات لا تناسب الخيارات.
  • إرشادات المقابلة: خطط، حضّر المُقابَل (موعد وأسئلة تمهيدية)، جهّز agenda وأسئلة، استمع وسجل، راجع الملاحظات خلال 48 ساعة، كن محايداً.
  • Individual interviews: أسهل جدولة؛ لكن تناقضات بين المقابَلين والمتابعة تأخذ وقتاً. Group interviews: استخدام أفضل للوقت، تسمع الاتفاق والاختلاف معاً؛ لكن جدولتها أصعب.
  • NGT (Nominal Group Technique): الأعضاء يجتمعون لكن يعملون منفردين أولاً، كل واحد يكتب أفكاره، المُيسّر يقرأها وتُكتب على السبورة، مناقشة ثم ترتيب وتحديد الأولويات.
  • Survey: قوة: رخيص، جمهور كبير، مناسب للمتفرقين جغرافياً، ممتاز للبيانات الكمية والتحليل الإحصائي. حدود: يحتاج مهارة sampling، قد تقل نسبة الاستجابة، الأسئلة المفتوحة تحتاج تحليل، الغموض.
  • Ethnography: مراقبة المستخدمين وهم يعملون (أدق من self-reporting). عيوب: المراقبة قد تغير سلوكهم، تعطي لقطة صغيرة، تأخذ وقتاً.
  • أنواع المستندات المفيدة (4): Written work procedures، Business forms، Reports، Description of current information system.
  • JAD: تقنية مكثفة جماعية لجمع المتطلبات من المستخدمين والمديرين والمحللين في نفس الوقت، في عزلة وفي مكان غير مكان عملهم المعتاد، وتحل التعارضات.
  • Prototyping: نموذج لتوضيح وتحقق المتطلبات تكرارياً. مفيد لما: طلبات المستخدم غير واضحة، مستخدمون قليلون، تاريخ من مشاكل التواصل. عيوب: صعب تعميمه، يحتاج فهماً تقنياً، توقعات غير واقعية، يركز على التصميم أكثر من الـ NFR.
  • أهمية elicitation (4): Stakeholder alignment، تقليل scope/feature creep، تحسين التواصل، تخفيف المخاطر مبكراً.
  • مشاكل elicitation (5): لا يعرفون ما يريدون؛ يعبرون بمصطلحاتهم؛ تعارض بين stakeholders؛ عوامل سياسية وتنظيمية؛ المتطلبات تتغير وتظهر أطراف جديدة.
  • طرق كتابة المواصفات (5): Natural language، Structured (template)، Design description languages، Graphical notations (UML)، Mathematical specs.
  • مشاكل natural language (3): lack of clarity، requirements confusion (خلط functional وNFR)، requirements combination (عدة متطلبات في جملة).
  • SRS: البيان الرسمي لما يُطلب من المطورين: user requirements + system requirements. المثالي: complete، unambiguous، بلا jargon، يوضح معلومات تشغيلية واستراتيجية، يحل الخلافات، يستخدم وسائل رسومية.
  • Best practices (4): clear & understandable، feasible & sensible، specific/accurate/complete (بلا عبارات ضعيفة مثل "fast")، testable.
  • Validation: إثبات أن المتطلبات تعرّف النظام الذي يريده العميل فعلاً. تصليح خطأ requirements بعد التسليم قد يكلف حتى 100 ضعف تصليح خطأ implementation.
  • Wireframes: هياكل منخفضة الدقة للموقع أو التطبيق. Requirements Management = إدارة المتطلبات المتغيرة. RTM (Traceability Matrix) تُظهر أثر التغيير المقترح على باقي المتطلبات وتتبع تقدم كل requirement.

  • 4 perspectives: External (context models)، Interaction (use case + sequence)، Structural (class diagram)، Behavioral (state diagram). UML diagram types: Activity, Use case, Sequence, Class, State.

المحاضرة 6: Scrum I

تنبيه Midtermالميدتيرم 15 درجة، يغطي المحاضرات 1–5، أسئلة مقالية. تعليمات القاعة: تجي قبل الوقت، بطاقة جامعية أو قومية، ممنوع الموبايل، أدوات الكتابة، اكتب الاسم والـ ID والمستوى والقسم، وقّع الحضور مرة واحدة ولا تخرج قبل تسجيل الحضور.

قبل ما تدخل لازم تعرف

  • Scrum: framework يساعد الفرق على العمل معاً، يصف مجموعة اجتماعات وأدوات وأدوار. هو subset من Agile، lightweight، وأكثر إطار agile انتشاراً.
  • فوائد Scrum (4): رفع جودة المخرجات، التعامل مع التغيير (ونتوقعه)، تقديرات أفضل بوقت أقل، تحكم أكبر في الجدول وحالة المشروع.
  • Scrum pillars معلومة عامة: Transparency, Inspection, Adaptation (الشريحة صورة من Scrum Alliance، راجعها).
  • Multilevel planning (4): Portfolio (أي منتجات نعمل وبأي ترتيب)، Product (vision ثم product backlog ثم roadmap)، Release (scope/date/budget trade-offs)، Sprint (يخرج منه sprint backlog، تخطيط just-in-time).
  • الأدوار: Product Owner (الـ backlog)، Scrum Master (العملية)، Development Team، وCustomer/Stakeholder.
  • الأدوار المجمّعة: ScrumMaster + عضو فريق = تضارب مصالح. الأفضل SM لأكثر من فريق. Product Owner لأكثر من فريق ممكن. PO + عضو فريق أحياناً. PO + SM على نفس الفريق فكرة سيئة لأن الدورين يوازن بعضهما فيحدث conflict of interest.
  • الفريق: أعضاء بـ T-shaped skills مع بعض المتخصصين. Musketeer attitude ("الكل للواحد والواحد للكل"، يربحون أو يخسرون كفريق). Focused: multitasking بين المنتجات يقلل الإنتاجية، 3 مشاريع أو أكثر خيار اقتصادي سيئ، اثنين كفاية. Sustainable pace.
  • Sprint: طول ثابت، عادة 2–4 أسابيع. نقطة البداية product backlog. الـ sprint goal لا يتغير أثناء الـ sprint، والعناصر الملتزم بها تبقى ثابتة. الفريق معزول وكل التواصل عبر Scrum master الذي يحميه من المشتتات. في النهاية: review وعرض على stakeholders.
  • Daily Scrum: يومياً. Sprint Review & Retrospective: في آخر يوم (أو قبله بيومين). Sprint Planning: أول يوم. Backlog Refinement: أثناء الـ sprint.
  • Artifacts: Product backlog، Sprint backlog، Potentially shippable product increment.
  • Definition of Done: قائمة تحقق: برمجة، بيانات اختبار، اختبار فعلي، قابلية النشر، توثيق (وليس "خلصت البرمجة" فقط).
  • Customer involvement: ممثل المستخدم متاح بدوام كامل، ويساعد في كتابة acceptance tests. المشكلة: قد لا يتوفر وقته. Coding standards: لا تعرف من كتب الكود، ويدعم collective ownership. Continuous Integration: دمج التغييرات فوراً وتشغيل كل الـ unit tests.

المحاضرة 7: Scrum II + User Stories + محاضرة الضيف

قبل ما تدخل لازم تعرف

  • User story: أصغر وحدة عمل في agile، تعبّر عن قيمة الـ feature للعميل. الصيغة: As a [role], I want [feature] so that [benefit].
  • 3Cs (Jeffries): Card (البطاقة)، Conversation (حوار مستمر يظهر منه sketch وقواعد عمل)، Confirmation (ظهر البطاقة: acceptance criteria).
  • Acceptance criteria بصيغة GWT: Given (سياق) ← When (فعل) ← Then (نتيجة ملاحظة). مثال: Given multiple categories exist, When I select a category, Then I should see only products in that category.
  • Levels: الـ Epic أكبر story (أشهر وقد تمتد لعدة releases).
  • INVEST معلومة عامة للحروف: Independent, Negotiable, Valuable, Estimable, Small, Testable. الشريحة تؤكد الـ Small: 6–10 stories تنتهي في sprint واحد، وما نعمل story بحجم الـ sprint كله.
  • Knowledge acquisition stories (spike): لما نفتقد المعرفة: prototype, proof of concept, experiment, study, spike. مخرجه عادة memo قصير.
  • Product backlog: قائمة مرتبة بالأولوية للوظائف المطلوبة. عناصره PBIs (غالباً user stories). Feature creep: إضافة features دون التأكد من فائدتها. أسبابه الثلاثة: المديرون لا يرفضون، المطورون يقلدون المنافسين، المنتج يخدم المبتدئين والخبراء.
  • DEEP: Detailed appropriately, Emergent, Estimated, Prioritized. (الشرائح تشرح Emergent وEstimated وPrioritized.)
  • التقدير: Planning Poker وT-shirt sizing. Story points مقابل ideal days. ماذا نقدر ومتى: Portfolio بـ XL/L/M/S، الـ PBI بـ story points أو ideal days، المهمة بـ ideal hours.
  • Velocity: كمية الشغل (story points) اللي الفريق ينجزها بالـ sprint. عدد الـ sprints = مجموع النقاط ÷ velocity. مثال: velocity = 20، backlog = 100 نقطة ← 5 sprints.
  • Backlog grooming/refinement (3 أنشطة): إنشاء وتحسين PBIs، تقديرها، ترتيب أولوياتها. صاحب القرار النهائي: Product Owner. يخصص الفريق حتى 10% من وقته كل sprint.
  • Definition of Ready: checklist لحالة العنصر قبل دخول الـ sprint. DoD vs Acceptance Criteria: DoD عام لكل story ومعيار جودة موحد (كود مراجَع، اختبارات ناجحة، توثيق، لا bugs)، أما acceptance criteria فخاصة بكل story.
  • الضيف (Ahmed Salah Elsisi، Senior BA): شهادات BA وScrum، و"Scrum bites": pillars, team, size, artifacts, events, accountabilities. معلومة عامة من Scrum Guide: الفريق عادة ≤ 10 أشخاص، artifacts = Product Backlog + Sprint Backlog + Increment، events = Sprint + Planning + Daily Scrum + Review + Retrospective، accountabilities = Product Owner + Scrum Master + Developers. الشرائح صور، راجعها.

من يتخذ قرار ترتيب الـ backlog؟ وكم وقت الفريق للـ grooming؟

المحاضرة 8: Product Management

قبل ما تدخل لازم تعرف

  • Product Manager: يضمن نجاح المنتج محلياً ودولياً، يحدد الفجوات وفرص النمو، يقود التطوير من الفكرة للإطلاق، يحدد ويرتب أهداف المنتج قصيرة وطويلة المدى، يتقن user journey وstory mapping، يجمع المتطلبات من العملاء والمبيعات والتسويق وR&D، ويدير الوثائق (PRDs، business requirements، use cases، user flows/stories، functional specs).
  • Product Owner: يعمل مع Product Management لإنشاء backlog حسب business value أو ROI، يرتب stories وepics، يكتب user stories وacceptance criteria، يقبل الـ features قبل UAT للعميل، ويدير change requests.
  • Competitive analysis (4): Customer analysis، Product analysis، Marketing analysis، SWOT.
  • SWOT: Strengths (ما نتميز به)، Weaknesses (عيوبنا مقارنة بالمنافسين)، Opportunities (عوامل خارجية للنمو)، Threats (مخاطر خارجية، لكن قد تكون داخلية مثل ارتفاع turnover).
  • طرق الأولويات (7): Kano، Value vs Complexity، Weighted Scoring، RICE، Eisenhower، Story Mapping، MoSCoW.
  • Kano: لذّة العميل مقابل الاستثمار؛ المنتج ليس وظيفة فقط بل مشاعر (الفرامل متوقعة، وparking-assist يبهر).
  • Value vs Complexity: محوران (Business Value وComplexity/Effort) وأربع خانات؛ عالي القيمة، قليل الجهد = low-hanging fruit تبدأ بها.
  • RICE = Reach, Impact, Confidence, Effort. Impact: 0.25 (minimal)، 0.5 (low)، 1 (medium)، 2 (high)، 3 (massive). Confidence: 100% عالية، 80% متوسطة، 50% منخفضة. Effort بـ person-months. معلومة عامة الصيغة: RICE = (Reach × Impact × Confidence) ÷ Effort.
  • Eisenhower: محور Urgent وImportant. الربع 1 (مهم+عاجل) = افعله الآن. الربع 2 (مهم، غير عاجل) = خطط له. الربع 3 (عاجل، غير مهم) = فوّضه. الربع 4 (لا مهم ولا عاجل) = لا يزاحم الأولويات.
  • Story Mapping: ترتيب الـ stories أفقياً على خطوات رحلة المستخدم زمنياً، وتحتها الـ stories.
  • MoSCoW: Must (لا غنى عنه، بدونه المنتج لا يعمل)، Should (أساسي لكن غير حيوي، يمكن تأجيله لـ release قادم)، Could (غير ضروري للـ core، أول ما يُلغى لو ضاق الوقت)، Won't (this time) (يمنع scope creep). مثال موقع المحامين: Must: برمجة بلا bugs، نظام تسجيل قوي، directory شخصي آمن. Should: سرعة، تصميم ممتاز، إشعارات إيميل. Could: custom menus، suggestions، blog. Won't: paid content، public members section، ads.

الفرق بين Product Manager وProduct Owner.

المحاضرة 9: Software Design Specifications

قبل ما تدخل لازم تعرف

  • SDD: وثيقة مكتوبة فيها كل المعلومات المهمة عن تصميم البرمجية ومعماريتها وكيف تُصمَّم بما يحقق المواصفات التقنية. المواصفات الجيدة: simple, complete, unambiguous.
  • SDD template (10 أقسام): Introduction، System Architecture، Detailed Design، Database Design (ERD)، UI/UX Design، Security Design، External Interfaces، Design for Testing، Constraints & Assumptions، Appendices.
  • مقاييس جودة الـ module (3): cohesion، coupling، fan-in/fan-out.
  • Cohesion: مدى ارتباط الأسطر داخل الـ module. نريدها High. Functional cohesion (كل العناصر لمهمة واحدة، الجيد)، Coincidental (لا علاقة بين الوظائف، الأسوأ). مزايا High cohesion: قراءة وفهم أفضل، عزل أفضل للأخطاء، reliability أعلى.
  • Coupling: درجة اعتماد module على آخر. نريدها Low (loosely coupled): واجهات بسيطة ونظيفة وأقل بيانات مشتركة. مزايا Low coupling: maintainability، modularity، scalability. مثال High coupling: Customer يخزن قائمة Orders وOrder يخزن reference للـ Customer، فهما tightly coupled. الحل: اجعل الـ association في اتجاه واحد (تخلص من أحد المرجعين).
  • Fan-in: عدد control modules التي تستدعي module. High fan-in = جيد (إعادة استخدام). Fan-out: عدد الـ subordinates لـ control واحد. تجنب high fan-out، والقاعدة حوالي 7.
  • Program specification: وثيقة مكتوبة فيها تعليمات تفصيلية لبرمجة module، واحدة لكل module. لا syntax رسمي. 4 مكونات: Program information، Events، Inputs & outputs، Pseudocode.
  • Reliability (3 تقنيات): Fault avoidance، Input validation، Failure management.
  • أنواع التعقيد (4): Reading، Structural، Data، Decision (Conditional).
  • إرشادات تقليل التعقيد: Structural: دالة تعمل شيئاً واحداً بلا side-effects، كل class مسؤولية واحدة (single responsibility)، قلّل عمق الوراثة، تجنب multiple inheritance والـ threads. Data: عرّف interfaces، تجنب floating-point، لا data aliases. Conditional: تجنب nested conditions والتعبيرات المعقدة.
  • Refactoring: تغيير البرنامج لتقليل تعقيده دون تغيير سلوكه الخارجي. Code smells (Martin Fowler): مؤشرات لمشكلة أعمق. أمثلة: Long methods، Duplicated code، Meaningless names، Unused/dead code.
  • أمثلة refactoring لتقليل التعقيد: Reading: إعادة تسمية. Data: دمج جداول DB المرتبطة. Decision: استبدال nested if-else بـ guard clauses.
  • Input validation: فحص أن المدخل بالصيغة والنطاق الصحيحين. حاسمة للأمان (SQL injection وbuffer overflow) والـ reliability. قواعد الاسم: طول 2–40 حرفاً، أحرف أبجدية (مع accents) وفواصل قليلة (hyphen وapostrophe)، يبدأ بحرف.
  • طرق التنفيذ (3): Built-in validation functions، Explicit comparisons (قوائم قيم مسموحة)، Regular expressions.
  • Number checking (تجنب overflow/underflow وافتراضات البرامج الأخرى) وRange checks (قراءة العداد ≥ السابقة ومتسقة مع الاستهلاك المعتاد).
  • Failure categories (3): Data failures (مخرجات غير صحيحة)، Program exceptions (حالة لا يمكن معها المتابعة، مثل ملف غير موجود IOException)، Timing failures (مكونات لا تستجيب في الوقت أو غير متزامنة).

Lab 1: Version Control باستخدام Git

قبل ما تدخل لازم تعرف

  • VCS: أداة تتبع التغييرات في الكود عبر الزمن وتسمح باسترجاع إصدارات سابقة. فوائده: الرجوع لنسخة سابقة، مقارنة الإصدارات، عمل عدة مطورين بالتوازي، معرفة من عدّل، branches، وهو backup للكود.
  • Git = Distributed VCS: كل نسخة عمل عند كل مطور هي repository فيها التاريخ كامل.
  • الإعداد: git config --global user.name "Name" و git config --global user.email "mail"
  • Commit: "صورة" لحالة كل الملفات في لحظة معينة. لو ملف ما تغير يخزن Git رابطاً للنسخة السابقة فقط.
  • 3 مناطق: Working directory ← Staging area ← .git directory (repository).
  • 4 حالات للملف: Untracked, Staged, Modified, Unmodified/Committed.
  • git init ينشئ مجلداً مخفياً .git.
  • نقطة مهمة: Git يعمل stage للملف كما هو لحظة git add. لو عدّلته بعدها يظهر staged وmodified معاً، وتحتاج git add مرة ثانية.
  • الـ commit يعطي hash مثل ef2d332، وعدد الملفات المتغيرة وإحصائيات الأسطر.
git init
git status
git add main.cpp        # أو git add .
git commit -m "message"
git log                 # git log -p -2 لآخر commitين مع التغييرات
git restore --staged main.cpp   # unstage (يحتفظ بالتعديلات)
git restore main.cpp            # يلغي التعديلات غير المضافة
git checkout <hash>             # الانتقال لـ commit قديم (detached HEAD)
git checkout main               # العودة لآخر commit
git reset --hard <hash>         # يرجع ويمسح كل ما بعده نهائياً (خطر!)
git tag -a V1.0 <hash> -m "desc"   # tag بدون hash = آخر commit
git checkout V1.0

أسئلة متوقعة

ما الفرق بين git restore --staged file و git restore file؟
الأول يشيل الملف من staging area لكن يترك التعديلات في working directory. الثاني يلغي نهائياً التعديلات غير المضافة (unstaged).
عدّلت ملفاً بعد git add ثم عملت commit. هل تدخل التعديلات الجديدة؟
لا. يدخل الـ commit النسخة كما كانت وقت آخر git add. التعديل الأخير يبقى modified ويحتاج git add جديد.
ما الفرق بين git checkout hash و git reset --hard hash؟
checkout ينتقل لمشاهدة commit قديم دون مسح شيء (ثم ترجع بـ git checkout main). reset --hard يجعل ذلك الـ commit هو الأحدث ويمسح كل ما بعده نهائياً.
ما فائدة الـ tags؟
علامات على commits مهمة تغنيك عن استخدام الـ hash، وتستخدمها في checkout.
ما الأوامر لإنشاء repo جديد وعمل أول commit؟
git init ← إنشاء main.cpp ← git add main.cpp ← git status ← git commit -m "msg" ← git status (لا تغييرات معلقة).

Lab 2: Branching & Merge Types

قبل ما تدخل لازم تعرف

  • .gitignore: ملف نصي يحدد الملفات التي يتجاهلها Git (auto-generated, logs, temp, personal). يُعمل commit له ليستفيد كل الفريق. إنشاؤه: npm install touch-cli -g ثم touch .gitignore.
  • Branch: خط تطوير منفصل (مساحة معزولة)، وهو في الحقيقة pointer خفيف متحرك يشير لـ commit. الافتراضي main أو master.
  • HEAD: pointer خاص يبين أين أنت الآن. git branch name ينشئ الفرع عند HEAD لكن HEAD لا يتحرك إليه. يتحرك بـ git checkout name. إذا أشار HEAD لفرع = symbolic pointer، وإذا أشار لـ commit مباشرة = detached HEAD.
  • عند commit جديد يتحرك الفرع الحالي وHEAD معاً. الفرع الحالي يظهر بـ * في git branch.
  • Fast-forward merge: يحدث لو فيه مسار مباشر من الفرع الحالي للفرع المدموج، فقط يحرك المؤشر (master ← dev). لا merge commit.
  • 3-way merge: لو لا يوجد مسار مباشر (الفرعان تفرّعا وكلاهما فيه commits جديدة). Git ينظر لثلاثة commits: base وآخر commit في كل فرع، وينشئ merge commit جديداً.
  • قاعدة الدمج: A change vs no-change → the change wins. وليس كل 3-way فيه conflict.
  • الفرع الحالي (checked out) هو الذي يتحدث، والفرع الهدف لا يتأثر.
git branch dev
git branch math-feature
git branch                              # عرض الفروع
git log --all --decorate --oneline --graph
git checkout master
git merge dev                           # fast-forward لو في مسار مباشر
git merge math-feature                  # 3-way merge

Lab 3: Conflicts, Delete Branch, Rebase, Stash

قبل ما تدخل لازم تعرف

  • Merge conflict: يحدث عندما يغيّر فرعان نفس الأسطر في نفس الملف بشكل مختلف (change vs change). Git يتوقف ويطلب منك حذف غير المرغوب وإبقاء المطلوب. لتحديده كـ resolved: stage + commit للملفات.
  • مثال المحاضرة: master غيّرت my_sum لتأخذ 3 أرقام، وmath-feature غيّرت الاسم لـ sum ← conflict. الحل المطلوب: int sum(int a, int b, int c) (نبقي التغييرين).

  • Rebase: ينقل commits فرعك فوق رأس الفرع الأساسي (ينسخها بـ hash جديد)، فيصبح التاريخ خطياً.

Lab 4: Cherry-pick + GitHub Collaboration

قبل ما تدخل لازم تعرف

  • Cherry-pick: يأخذ commit محدداً (بالـ hash) من فرع آخر ويطبقه على فرعك الحالي دون دمج الفرع كله. الخطوات: git log لمعرفة الـ hash ← checkout للفرع الهدف ← git cherry-pick hash. الخيار --no-commit يطبق التغييرات ويضعها في staging دون commit.
  • خدمات الاستضافة: GitHub, BitBucket, GitLab. مزايا GitHub: Access control، Code reviews، Issues tracking، CI/CD (Actions)، Web hosting (Pages).
  • git clone URL ينسخ كل الريبو (ملفات وتاريخ وbranches). git remote add origin URL يربط ريبو محلي بـ remote. git push -u origin main (أول مرة). فقط المالك والـ collaborators يقدرون يعملون push.
  • fetch vs pull: git fetch يجلب التغييرات فقط ولا يطبقها (تراجعها أولاً)، ثم git merge origin/Branch. git pull = fetch + merge.
  • فرع جديد على remote: git push --set-upstream origin BranchName.
  • Pull Request (PR): طلب دمج فرع في base branch. فوائده: مراجعة الكود قبل الدمج، وتوثيق لسبب وكيفية التغيير. التعليق على الكود ممكن، والـ commits الجديدة تظهر تلقائياً في الـ PR.
  • 3 طرق الدمج في GitHub: Merge commit (ينشئ merge commit ويحفظ التاريخ)، Rebase and merge (يعيد commits فوق الهدف، تاريخ خطي)، Squash and merge (يجمع كل commits الـ PR في commit واحد).
  • حل conflicts في PR: checkout main ← git pull ← checkout feature ← git merge main ← حل التعارضات ← stage وcommit ← git push.
  • Fork: نسخة شخصية من ريبو الغير، تعدل فيها وتقدم PR للأصل.
  • GitHub workflow (8 خطوات): create/fork، clone، feature branch، commits، push، open PR، discuss، owner يدمج أو يغلق.
  • Best practices (5): commit متكرر وصغير، حدّث نسختك بـ pull، رسائل commit واضحة، راجع عبر PRs، branch لكل feature.

أسئلة متوقعة

متى نستخدم cherry-pick؟
لما نريد تطبيق commit واحد (مثل إصلاح bug حرج) على main دون دمج feature-branch غير الجاهز.
الفرق بين fetch وpull.
fetch يحدّث نسخة remote المحلية فقط دون تغيير فرعك الحالي. pull = fetch ثم merge تلقائياً.
قارن بين Merge commit وRebase and merge وSquash and merge.
Merge commit: يحفظ التفاصيل مع commit إضافي. Rebase: تاريخ خطي. Squash: يضغط عدة commits في واحد لتاريخ أنظف.
ما فائدة الـ Pull Request؟
مراجعة الكود قبل الدمج للإمساك بالمشاكل وتحسين الجودة، وتوثيق التاريخ وسبب التعديلات.
رتّب خطوات: إنشاء repo على GitHub وclone وتعديل وpush ثم PR ثم الدمج.
create repo ← git clone ← git checkout -b/branch ← add & commit ← git push --set-upstream origin new-feature ← Create PR ← comment ← merge ← git checkout main ← git pull.

Lab 5: CI/CD مع GitHub Actions

قبل ما تدخل لازم تعرف

  • Production: البيئة الحية التي يستخدمها المستخدمون الحقيقيون. Deployment: نقل الكود/التحديثات من بيئة الاختبار إلى production.
  • المشكلة: دمج commits دون تشغيل الاختبارات قد يكسر النظام (مثال: كل المنتجات صارت مجانية). الحل: CI/CD.
  • CI: دمج التغييرات بشكل متكرر في codebase مشترك مع اختبار آلي لكل تغيير لاكتشاف المشاكل مبكراً.
  • Continuous Delivery: بعد CI يُجهّز الكود تلقائياً ليكون جاهزاً للإصدار، وغالباً موافقة يدوية نهائية قبل production. Continuous Deployment: كل تغيير ينجح في الاختبارات يُنشر إلى production تلقائياً دون تدخل بشري.
  • GitHub Actions: منصة CI/CD تؤتمت build وtest وdeploy.
  • Workflow: عملية آلية تعمل عند وقوع event في الريبو (push, pull request). مكوناتها: event أو أكثر، job أو أكثر. كل job يعمل في runner (VM) خاص به وفيه steps. الـ step إما shell script (run) أو action (uses).
  • الـ jobs افتراضياً تعمل بالتوازي ويمكن جعل job يعتمد على آخر. الـ steps تعمل بالترتيب على نفس الـ runner. الـ runner: Ubuntu / Windows / macOS، ويشغّل job واحداً في كل مرة في VM جديدة.
  • Action: إضافة قابلة لإعادة الاستخدام (مثل built-in functions)، مثل actions/checkout@v4 الذي ينزل كود الريبو إلى الـ runner (ضروري لأن الـ VM لا يملك كودك).
  • الـ workflow ملف YAML داخل .github/workflows/ في جذر الريبو. الريبو يقدر يحوي عدة workflows.
  • Context: كائن فيه معلومات عن التشغيل، الصيغة ${{ runner.os }}.
name: GitHub Actions Demo
on: push                       # أو [push, pull_request]
jobs:
  Explore-GitHub-Actions:
    runs-on: ubuntu-latest
    steps:
      - name: Print the triggering event
        run: echo "The job was triggered by ${{ github.event_name }}."
      - name: Check out repository code action
        uses: actions/checkout@v4
      - name: List files in the repository
        run: ls ${{ github.workspace }}

Lab 7: مقدمة Jira

قبل ما تدخل لازم تعرف

  • Jira: أداة #1 لإدارة مشاريع agile (Scrum وKanban): boards، backlogs، roadmaps، reports. من تطوير Atlassian الأسترالية. الاسم من Gojira (Godzilla بالياباني).
  • منتجات Atlassian: Jira Work Management (لفرق الأعمال غير التقنية)، Confluence (توثيق ومعرفة)، Trello.
  • Jira vs Trello: Jira للمشاريع المعقدة والكبيرة، دعم agile مدمج (sprints)، تقارير متقدمة (Burndown, Velocity)، يتوسع للمؤسسات، تتبع مفصل (Epics, Stories, Bugs). Trello للمشاريع البسيطة/الصغيرة، boards أساسية، تقارير بسيطة.
  • Project: مجموعة issues، له اسم وkey (مثل SSP)، والـ key هو بداية issue key (SSP-15). نوعان: Team-managed (يديره الفريق، مرن) وCompany-managed (يديره الـ admins، قياسي للمؤسسات الكبيرة).
  • Epic: عمل كبير يتفكك لـ issues، يمتد لعدة sprints. Issue types (5): Story (من منظور المستخدم)، Task (عمل عام مثل setup database)، Bug (عيب)، Sub-task (جزء أصغر)، Epic.
  • Priority (5): Highest (blocker، فوري)، High، Medium (الافتراضي)، Low، Lowest.
  • Status types: To Do, In Progress, In Review, Done, Blocked, Reopened. وحقل Resolution مهم في الـ bugs (fixed, duplicate, incomplete, done).
  • الحقول: Project, Key, Summary, Type, Status, Priority, Resolution, Affects Version(s), Fix Version(s), Epic, Labels, Description, Links, Assignee (المسؤول)، Reporter (من أدخل الـ issue)، Votes, Watchers, Due, Created, Updated, Resolved, Estimate (الأصلي)، Remaining، Logged (الوقت المصروف).
  • Board: تمثيل مرئي للـ workflow. Workflow: مراحل ينتقل فيها الـ issue والـ transitions بينها (الافتراضي To Do → In Progress → Done). Backlog: قائمة الشغل غير البادئ وغير المخصص لـ sprint. Sprint: iteration محددة الزمن (1–4 أسابيع). Version/Release: مجموعة issues المنجزة التي تُنشر معاً (milestone مثل Q1 Release) وقد تشمل عدة sprints.
  • Integrations: GitHub/GitLab/Bitbucket (تتبع commits وbranches وPRs داخل الـ issue)، Jenkins (CI/CD)، Figma (ربط التصاميم)، Xray (إدارة الاختبارات: Test, Precondition, Test Set, Test Plan, Test Execution)، Slack (إشعارات).
  • إضافة مستخدمين بنفس الإيميل: أضف علامة + بعد اسم الإيميل ثم alias (email+dev@domain.com).
  • ربط GitHub: Apps ← "GitHub for Jira" ← Connect GitHub Organization ← authorize ← اختر الريبوهات. للتحقق: أنشئ branch من الـ issue وcommit وPR ثم راجع قسم Development في الـ issue.

قارن بين Jira وTrello.
انظر الجدول أعلاه: Jira أقوى للمشاريع المعقدة (Scrum/Kanban وreports)، وTrello أبسط للمشاريع الصغيرة.

Assignee: المسؤول الحالي. Reporter: من أدخل الـ issue. Affects: الإصدار الذي ظهرت فيه المشكلة. Fix: الإصدار الذي أُصلحت/ستُصلح فيه.

إضافة لإدارة الاختبارات داخل Jira. تنشئ issue من نوع Test وتربطه بالـ Story، ثم Test Execution لتنفيذه وتسجيل Pass/Fail، وTest Plan لمتابعة التقدم.

Lab 9: Refactoring

ملاحظةأمثلة الكود في شرائح هذا اللاب صور (C#)، وما قدرت أقراها، فالشرح هنا للأنواع التسعة بتعريفها المعروف معلومة عامة مع ربطها بوصف المهام. راجع الصور في الشرائح 12–31.

قبل ما تدخل لازم تعرف

  • Clean code: واضح لبقية المبرمجين، بلا تكرار، أقل عدد من الـ classes والأجزاء المتحركة، يجتاز كل الاختبارات، أسهل وأرخص صيانة.
  • Refactoring: تغيير الكود الحالي ليصبح أسهل قراءة وتعديل مع الحفاظ على الوظيفة؛ عملية مستمرة وبـ خطوات صغيرة متزايدة.
  • لماذا؟ Technical debt. أسباب تحول الكود النظيف إلى غير نظيف: ضغط business، عدم فهم عواقب technical debt، coupling قوي بين المكونات، قلة الاختبارات، قلة التوثيق، ضعف التواصل، تطوير طويل في عدة branches، تأخير refactoring، قلة المراقبة، عدم الكفاءة.
  • متى؟ Rule of Three: أول مرة تنفذ فقط، ثاني مرة تتضايق وتكرر، ثالث مرة ابدأ refactoring. أيضاً: عند إضافة feature، عند إصلاح bug، أثناء code review.
  • أهدافه: تصميم أفضل، تعقيد أقل، readability، maintainability، معمارية أفضل. لو تم بشكل سيء قد يغير الوظيفة أو يضيف bugs.
  • SOLID: Single Responsibility (class واحد لمسؤولية واحدة)، Open-Closed (مفتوح للتوسعة، مغلق للتعديل)، Liskov Substitution (الـ subclass يحل محل الـ superclass دون كسر النظام)، Interface Segregation (لا نجبر client على الاعتماد على methods لا يستخدمها)، Dependency Inversion (high-level لا يعتمد على low-level، كلاهما على abstractions).

  • DevOps = Development + Operations. أهدافه: سد الفجوة، أتمتة كل شيء (test/build/deploy)، إصدارات صغيرة ومستمرة، بيئات موحدة (Docker)، مراقبة مستمرة وتغذية راجعة.
  • CI يحل مشكلة المطورين (تحقق مبكر ومتكرر). CD يحل مشكلة الـ Ops (نشر آمن وآلي ومتكرر).
  • خطوات العملية: Development (Git/GitHub) ← CI (GitHub Actions: build + tests؛ إذا فشل أي test يتوقف الـ workflow ويُشعَر المطورون) ← Containerization (Docker) ← CD (GitHub Actions) ← Orchestration (Kubernetes) ← Monitoring & Feedback.
  • أنواع الاختبارات: Unit (دوال منفردة)، Integration (عدة أجزاء معاً)، Smoke (فحص سريع أساسي: هل التطبيق يشتغل؟ login؟ الصفحة الرئيسية؟). الاختبارات يصممها الـ testers وGitHub Actions فقط يشغّلها آلياً.
  • Docker: container خفيف وثابت البيئة يشغّل التطبيق بنفس السلوك على أي جهاز. الـ Docker image يُرفع إلى container registry (Docker Hub / GitHub Container Registry).
  • Continuous Delivery: يبني ويخزن الـ image وينتظر الموافقة (مدير/team lead). Continuous Deployment: ينشر تلقائياً على cloud (AWS/Azure/Google Cloud).
  • Kubernetes (K8s): orchestration، يتحكم تلقائياً في إنشاء الـ containers وتوسيعها (scaling) وإصلاحها (healing)، مع load balancing.
  • Monitoring: Prometheus، CloudWatch؛ logs وmetrics تعود لدورة DevOps؛ عند المشاكل alerts تؤدي لـ rollback أو إصلاح.
ما الفرق بين unit وintegration وsmoke tests؟
Unit يفحص دالة منفردة، Integration يفحص عدة أجزاء تعمل معاً، Smoke فحص سريع أن الوظائف الأساسية تعمل (التطبيق يفتح، login، الصفحة الرئيسية).
ما دور Docker وKubernetes؟
Docker يغلّف التطبيق وبيئته في container ثابت. Kubernetes يدير عدداً كبيراً من الـ containers: scaling وload balancing وhealing.
