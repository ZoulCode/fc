المحاضرة 1: SDLC وأساسيات Business Analysis

الفكرة الكبيرة

أي نظام برمجي (مستشفى، متجر، تطبيق جامعة) بيمر بنفس المراحل بالترتيب. الدورة دي اسمها SDLC (Systems Development Life Cycle). تخيلها زي بناء بيت.

المراحل الست (بمثال نظام مستشفى)

المرحلةالسؤال اللي بتجاوب عليهمثال

Analysisمين بيستخدمه؟ بيعمل شنو؟ وين ومتى؟تسأل الدكاترة والممرضين عن احتياجاتهم

Implementationنبنيه ونركّبهكتابة الكود، فحصه، تركيبه، دعم المستخدمين
Testingشغال صح؟اختبار البرامج المنفردة والنظام كله

مخرجات الـ SDLC ثلاثة: software، توثيق عن النظام وكيف اتبنى، وتدريب للمستخدمين.

  • مخرجها system proposal رسمي يساعد الإدارة تقرر تكمل ولا لا.
  • خطواتها الثمانية: تكوين فريق وقائد ← رسم flowcharts ← تحديد عيوب النظام الحالي وأهدافك ← تعداد البدائل ← تقييم جدوى كل بديل ← وزن الأداء والتكلفة ← ترتيب البدائل واختيار الأفضل ← إعداد proposal للإدارة.

Business Analyst مقابل System Analyst

Business AnalystSystem Analyst

مهارات الـ System Analyst ست: technical، business، analytical، interpersonal، management، ethical.

Core Concept Model (ست مفاهيم)

  • Need: مشكلة أو فرصة محتاجة معالجة.
  • Change: التحول اللي بيحصل استجابة للحاجة.
  • Solution: طريقة محددة لتلبية الحاجة في سياق معين.
  • Stakeholder: أي فرد أو مجموعة ليهم علاقة بالتغيير أو الحاجة أو الحل (عميل، end user، sponsor، tester، regulator، supplier...).
  • Value: قيمة الشيء لـ stakeholder. Tangible (تتقاس مباشرة، مثل المال) أو Intangible (غير مباشرة، مثل سمعة الشركة وروح الموظفين).
  • Context: الظروف المحيطة اللي بتأثر على التغيير (ثقافة، منافسين، قوانين، تقنية...).

CASE Tools وOutsourcing

  • CASE tools: أدوات بتساعد في كل مراحل الـ SDLC: diagramming، مولدات شاشات وتقارير، أدوات تفحص التناقض في المواصفات، مولدات توثيق، مولدات كود. قلبها هو الـ repository، قاعدة بيانات موحدة بتخزن كل مخرجات المشروع. أمثلة: Oracle Designer وRational Rose وEclipse.
  • Outsourcing: إسناد جزء من أنظمة المؤسسة لشركة خارجية. أسبابه: توفير التكلفة، تفريغ موارد داخلية، تقليل time-to-market، رفع كفاءة العمليات، أو لأن تطوير النظم نشاط غير أساسي للمؤسسة.

Lab 1: Version Control باستخدام Git

المشكلة اللي Git بيحلها

الساعة 1 صباحاً، التسليم بكرة، ومسحت ملف مهم بالغلط. الحل البدائي نسخ بأسماء زي final وfinal2 وfinal_NEW: سهل لكن عرضة للأخطاء (تنسى أي نسخة الأحدث أو تكتب فوق ملف غلط). Version Control System بيسجل كل تغيير عبر الزمن، فتقدر ترجع لأي نسخة، وتقارن، وتعرف مين غيّر شنو، وفريق كامل يشتغل في نفس الوقت، وهو كمان backup للكود.

Git هو Distributed VCS: كل مطور عنده نسخة كاملة بكل التاريخ، مش بس سيرفر مركزي واحد.

كيف Git يفكر

Commit = لقطة (snapshot) لكل ملفات المشروع في لحظة معينة. لو ملف ما اتغير، Git ما بيخزنه تاني، بيحط رابط للنسخة القديمة (سريع وخفيف).

Working Directory --git add--> Staging Area --git commit--> .git (Repository)
 (أنت بتعدل هنا)          (جاهز للـ commit)           (التاريخ المحفوظ)

أربع حالات للملف: Untracked (Git ما يعرفه) ← Modified (متتبع واتعدل) ← Staged (اتضاف) ← Committed (محفوظ).

أهم نقطة في اللاب (بتتنسى كتير)Git بيعمل stage للملف زي ما هو لحظة git add. لو عدلته بعدها، git status بيورّيك الملف مرتين (staged وmodified). لو عملت commit دلوقتي، التعديل الأخير ما بيدخل. لازم git add تاني.

جلسة كاملة بالأوامر

git config --global user.name "Basem"      # مرة واحدة بس
git config --global user.email "me@mail.com"

mkdir demo && cd demo
git init                  # ينشئ مجلد .git المخفي (التاريخ كله هنا)

# أنشئ main.cpp ثم:
git status                # Untracked files
git add main.cpp          # أو git add . لكل الملفات
git status                # Changes to be committed
git commit -m "first commit"
git status                # nothing to commit

بعد الـ commit بيطلع hash زي ef2d332 وعدد الملفات المتغيرة والأسطر المضافة والمحذوفة.

التراجع والتنقل بين النسخ

git log                         # كل الـ commits
git log -p -2                   # آخر commitين بالتفاصيل

git restore --staged main.cpp   # يشيل الملف من staging، والتعديلات تفضل
git restore main.cpp            # يلغي تعديلاتك نهائياً (احذر!)

git checkout <hash>             # تتفرج على نسخة قديمة (detached HEAD)
git checkout main               # ترجع لآخر نسخة

git reset --hard <hash>         # يرجع للـ commit ده ويمسح كل اللي بعده نهائياً
الفرق المهمcheckout بس تتفرج وما بيمسح شيء. reset --hard بيمسح فعلاً، فاستخدمه بحذر.

Tags

اسم سهل لـ commit مهم بدل الـ hash الطويل.

git tag -a V1.0 <hash> -m "first release"   # من غير hash يوسم آخر commit
git checkout V1.0                            # تنتقل بالاسم

الـ Hands-on الثلاثة (طبّقها بإيدك)

  1. Hands-on 1: git init ← ملف main.cpp ← add ← status ← commit ← status.
  2. Hands-on 2: عدل الملف ← add ← restore --staged ← restore ← عدل تاني ← add ← commit ← log.
  3. Hands-on 3: git log ← خذ hash أول commit ← اعمل tag ← checkout بالـ tag ← ارجع بـ checkout main.
سؤال: عدلت ملف بعد git add وعملت commit مباشرة، شنو بيدخل؟
النسخة كما كانت وقت آخر git add. التعديل الأخير يفضل modified ويحتاج add جديد.
سؤال: الفرق بين git restore --staged f وgit restore f؟
الأول يشيل الملف من staging والتعديلات تفضل في working directory. الثاني يلغي التعديلات غير المضافة نهائياً.

المحاضرة 2: Project Planning

الفكرة الكبيرة

التخطيط معناه تقسيم الشغل لأجزاء وتوزيعها على الفريق، وتتوقع المشاكل وتجهز حلول مبدئية لها. الخطة بتتكتب في أول المشروع وبتُستخدم لتوصيل "كيف حنشتغل" للفريق والعملاء، ولقياس التقدم.

مراحل التخطيط الثلاث

المرحلةمتى؟الهدف
Proposalوأنت بتتنافس على عقدمعلومات لتسعير النظام (التكلفة: موظفين، hardware، software)، وعندك متطلبات مبدئية بس
Project startupبعد الفوز بالعقدمين يشتغل، كيف يتقسم المشروع لـ increments، وكيف تتوزع الموارد. تعرف المتطلبات لكن ما عندك تصميم. تحدد كمان آليات المتابعة. حتى الـ agile يحتاج startup plan

Software Pricing (التسعير)

التكلفة اللي عليك مش هي بالضرورة السعر للعميل. اعتبارات تنظيمية واقتصادية وسياسية بتأثر. العوامل الخمسة (احفظها):

العاملالفكرة
Contractual termsلو العميل يسمح للمطور يحتفظ بملكية الكود ويعيد استخدامه، السعر أقل. لو الكود يتسلم للعميل، السعر أعلى
Cost estimate uncertaintyلو مش متأكد من تقديرك، بترفع السعر بهامش (contingency) فوق ربحك المعتاد
Financial healthشركة في ضائقة بتخفض السعر عشان تكسب العقد. السيولة (cash flow) أهم من الربح في الأوقات الصعبة
Market opportunityتقبل ربح قليل لتدخل شريحة سوق جديدة وتكسب أكتر بعدين وتتعلم منتجات جديدة

  • Under pricing: لكسب عقد يخلي الموظفين شغالين، أو لدخول سوق جديد.
  • Increased pricing: لما المشتري يريد fixed-price، فالبائع يرفع السعر لتغطية المخاطر غير المتوقعة.

Plan-driven Development

نهج بتخطط فيه العملية بالتفصيل (الطريقة التقليدية للمشاريع الكبيرة). الخطة بتسجل الشغل ومين يعمله والجدول والمنتجات.

  • مع: التخطيط المبكر بيحسب القضايا التنظيمية (توفر الموظفين، مشاريع أخرى)، وبيكشف المشاكل والـ dependencies قبل البدء.
  • ضد: قرارات مبكرة كتيرة بتحتاج تعديل لأن البيئة بتتغير.

الـ Project Plan

أقسامه السبعة: Introduction ← Project organization ← Risk analysis ← Hardware & software resource requirements ← Work breakdown ← Project schedule ← Monitoring & reporting mechanisms.

الخطط الإضافية الخمس:

الخطةبتصف
Configuration managementإجراءات وهياكل إدارة التكوين والتغيير
Deploymentكيف يتنشر الـ software والـ hardware في بيئة العميل، وخطة نقل البيانات من الأنظمة القديمة
Maintenanceتوقع متطلبات الصيانة وتكلفتها وجهدها
Qualityإجراءات ومعايير الجودة
Validationمنهج وموارد وجدول التحقق من النظام

عملية التخطيط والمخاطر

  • التخطيط تكراري (iterative). تغيير الخطط حتمي لسببين: ظهور معلومات جديدة عن النظام والفريق، وتغير أهداف العمل (ممكن يأثر على كل المشاريع فيعاد تخطيطها).
  • افتراضات واقعية مش متفائلة، وأضف contingency (هامش أمان) عشان لو حصلت مشاكل جدول التسليم ما يتعطل بشكل خطير.
  • لو مشاكل كبيرة بتسبب تأخير: ابدأ risk mitigation (إجراءات لتقليل خطر الفشل)، وأعد التخطيط، وقد تحتاج تعيد التفاوض مع العميل على القيود والـ deliverables، وتتفق على جدول جديد.

Project Scheduling (الجدولة)

قرار كيف يتنظم الشغل كمهام منفصلة، ومتى وكيف تتنفذ. بتقدر وقت كل مهمة والجهد ومين يشتغل، والموارد (مساحة سيرفر، وقت على hardware متخصص، ميزانية سفر).

الأنشطة الأربعة: تقسيم المشروع لمهام وتقدير وقتها ومواردها ← تنظيم المهام بالتوازي لاستخدام أمثل للقوى العاملة ← تقليل الـ dependencies لتجنب انتظار مهمة لأخرى ← كله بيعتمد على حدس وخبرة مدير المشروع.

مشاكل الجدولة الأربع:

  1. تقدير صعوبة المشكلة وتكلفة حلها صعب.
  2. الإنتاجية ما بتتناسب مع عدد الناس.
  3. إضافة ناس لمشروع متأخر بتؤخره أكتر بسبب الـ communication overhead.
  4. غير المتوقع بيحصل دايماً، فاترك contingency.

كل activity لازم يكون ليها: duration بالأيام، effort بـ person-days، deadline، وfinishing point محدد (وثيقة أو اجتماع مراجعة أو نجاح كل الاختبارات). والمهام ما تكون صغيرة جداً: حوالي أسبوع أو أسبوعين.

MilestoneDeliverable
نقطة في الجدول تقيس عندها التقدم، مثل تسليم النظام للاختبارمنتج عمل بيتسلم للعميل، مثل وثيقة المتطلبات

أدوات التخطيط: Basecamp وMicrosoft Project (تدخل المعلومات في جدول وتولد bar charts وactivity charts تلقائياً).

طرق عرض الجدول

  • Bar chart (calendar-based): الأنشطة مقابل الزمن. الأكتر استخداماً.
  • Activity network: بتوضح الـ dependencies بين المهام (أسهم وعُقد)، وهي اللي بتحدد الـ critical path.

Critical Path (الجزء الحسابي المهم)

الـ critical path هو أطول مسار في الشبكة، وهو بيحدد أقل وقت ممكن لإنهاء المشروع. أي تأخير في مهمة عليه بيؤخر المشروع كله.

القاعدة: المهمة ما تبدأ إلا لما تخلص كل المهام اللي معتمدة عليها، يعني بتأخذ أكبر وقت انتهاء بين الـ dependencies (مش المتوسط).

مثال البيت: الخطوات A وB وC بالتسلسل. D وE وF بالتوازي. G وH بعدهم. الخطوة H ما تبدأ إلا بعد انتهاء D وE وF كلهم، فالأطول هو اللي يحدد. D هي الأطول، فالـ critical path يمر عبر D وG. بجمع أزمنة الـ critical path:

Lab 2: Branching وأنواع الـ Merge

مراجعة سريعة

  • الـ commit بيحفظ حالة الملفات في لحظة معينة، وعادة بنعمله لما وحدة منطقية من الشغل تخلص (مثلاً feature جديد).
  • مجلد .git فيه قاعدة بيانات الكائنات وبيانات الـ repo. لو أرسلته لشخص، عنده المشروع كاملاً وكل نسخه.

ملف .gitignore

ملف نصي بيقول لـ Git "تجاهل الملفات دي". من غيره Git بيتتبع كل ملف في المجلد. نستخدمه للملفات المولّدة تلقائياً، والخاصة بالمنصة، وملفات الـ log، والمؤقتة، والشخصية. لازم يتعمل له commit عشان كل الفريق يستفيد.

npm install touch-cli -g

الـ Branch: الفكرة

عندك فكرة feature جديد وما متأكد تنجح، ومش عايز تخرب النسخة الشغالة. الـ branch هو خط تطوير منفصل (مساحة معزولة) تجرب فيه وتعمل commits بدون ما تأثر على الكود الأساسي لحد ما تقرر تدمجه. الاسم الافتراضي: main أو master (الشرائح بتستخدم master).

الحقيقة التقنية المهمةالـ branch في الواقع مجرد pointer خفيف متحرك بيشاور على commit. لما بتعمل commits جديدة المؤشر بيتحرك لقدام تلقائياً. إنشاء branch جديد = إنشاء pointer جديد (فهو سريع جداً).

HEAD: كيف Git يعرف إنت وين؟

  • HEAD pointer خاص بيشاور على الـ branch الحالي.
  • git branch name بينشئ الـ branch عند مكان HEAD، لكن HEAD ما بيتحرك ليه. بتنتقل بـ git checkout name.
  • لما HEAD يشاور على branch: symbolic pointer. لما يشاور على commit مباشرة (مثل checkout hash): detached HEAD.
  • الـ branch الحالي بيظهر بعلامة * في git branch.
  • لما تعمل commit جديد، بيتحرك الـ branch الحالي وHEAD معاً.

أوامر أساسية

git branch dev              # ينشئ فرع (HEAD ما يتحرك)
git branch                  # يعرض الفروع
git checkout dev            # ينتقل ويحرك HEAD
git log --all --decorate --oneline --graph   # رسم التاريخ
git status                  # يقول لك أنت على أي فرع

معلومة عامة خارج الشرائح: git checkout -b name بينشئ الفرع وينتقل ليه بأمر واحد.

dev، ولو عملت commit فقط dev بيتقدم.

النوع الأول: Fast-forward Merge

بعد ما عملت commits على dev عايز تدمجها في master:

git checkout master      # الأول خلي HEAD على الفرع اللي حيستقبل
git merge dev
  • الفرع الحالي (master) هو اللي بيتحدث. الفرع المدموج (dev) ما بيتأثر.
  • لو في مسار مباشر (direct path) من master لـ dev، Git بيعمل fast-forward: بس بيحرك مؤشر master لقدام لنفس مكان dev. ما في commit جديد.
قبل:   C0 --- D1          (master عند C0، dev عند D1)
بعد:   C0 --- D1          (master و dev الاتنين عند D1)

النوع الثاني: 3-way Merge

لو master اتقدم لقدام وبعدين دمجت math-feature اللي طلعت من نقطة أقدم، ما في مسار مباشر. الفرعان تباعدا:

        D1  (master)
       /
C0 ---+
       \
        M1  (math-feature)

Git ينظر لـ ثلاثة commits: الـ base (نقطة التفرع C0)، وآخر commit في master، وآخر commit في math-feature. ثم ينشئ merge commit جديد بأبوين.

git checkout master
git merge math-feature    # 3-way: ينشئ merge commit

        D1 ------- X   (X = merge commit، master)
       /          /
C0 ---+          /
       \        /
        M1 ----+

السؤال في الشرائح: هل كل 3-way merge ينتج conflict؟ لا. الـ conflict ما بيحصل إلا لو الفرعان عدلا نفس الأسطر.

Hands-on 3 (الأهم: نوع الـ merge ولماذا؟)

السيناريو: master دمجنا فيه dev (fast-forward) ثم math-feature (3-way). الآن:

  1. ادمج master في dev.
  2. ادمج master في math-feature.
  3. هل كل الفروع تشاور على نفس الـ commit؟

جربت السيناريو ده فعلياً على Git وده اللي طلع:

--- merge master into dev:           Fast-forward
--- merge master into math-feature:  Fast-forward

*   cf684c6 (HEAD -> math-feature, master, dev) Merge branch 'math-feature'
|\
| * 154428d M1 add sum
* | 3952a74 D1 dev change
|/
* cebb1d3 C0 initial
الجوابالاتنين fast-forward. السبب: master بعد الدمج بقى يحتوي على كل commits الفرعين (merge commit بأبوين: D1 وM1)، فـ dev وmath-feature كلاهما أسلاف لـ master، يعني في مسار مباشر ليهم لقدام، فـ Git بس يحرك المؤشر. والجواب على السؤال الثالث: نعم، كل الفروع تشاور على نفس الـ commit ونفس الكود.

تذكر القاعدة: fast-forward لما الفرع الحالي سلف مباشر للفرع المدموج. 3-way لما الاتنين تباعدوا.

أسئلة للتدريب

متى يحدث fast-forward ومتى 3-way؟
FF لما فيه direct path (الفرع الحالي لم يتقدم بعيداً عن الفرع المدموج). 3-way لما الفرعان تباعدا، فيحتاج merge commit.
ليه لازم أعمل checkout لـ master قبل ما أدمج dev فيه؟
لأن الـ merge بيحدّث الفرع الحالي (اللي HEAD عليه) ويدمج فيه الفرع المحدد. الفرع المدموج ما بيتغير.
ما هو الـ branch فعلاً؟
pointer خفيف متحرك يشاور على commit، وبيتحرك لقدام تلقائياً مع كل commit جديد.
الفرق بين HEAD الـ symbolic والـ detached؟
symbolic: HEAD يشاور على branch. detached: HEAD يشاور على commit مباشرة (مثل git checkout hash).
هل كل 3-way merge ينتج conflict؟
لا. ينتج فقط لو الفرعان عدلا نفس الأسطر في نفس الملف بشكل مختلف. غير كده قاعدة "التغيير يكسب على عدم التغيير" بتحل الأمر تلقائياً.
