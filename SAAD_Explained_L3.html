المحاضرة 3: Requirements (المتطلبات)

الفكرة الكبيرة

قبل ما تبني أي نظام لازم تعرف بالظبط شنو المطلوب. أغلب فشل المشاريع سببه إن الناس فهموا المطلوب غلط. المتطلبات هي الأساس اللي كل المراحل بعده بتبنى عليه.

شنو هو الـ Requirement؟

تمثيل قابل للاستخدام لـ need (حاجة). وهو بيحدد واحد من أربعة:

يحددمثال من الشرائح
Feature لازم الحل يتيحهCloud Access
Function لازم الحل ينفذهاCalculate Savings
Fact لازم الحل يفرضهالالتزام باللوائح والقوانين
Quality لازم الحل يحققهافتح الملف في ثانية واحدة

تصنيف المتطلبات (أربعة أنواع)

النوعالفكرةمثال
Businessأهداف عليا، بتجاوب "لماذا المشروع مطلوب؟". بيحددها المستوى التنفيذي في وثيقة BRD (Business Requirements Document)"المستشفى يحتاج تقليل زمن انتظار المرضى"
Stakeholderاحتياجات ورغبات stakeholder وكيف حيتفاعل مع الحل. هي الجسر بين Business وSolution. بتقول "ما المطلوب" مش "كيف""As a doctor, I need to see a patient's history so I can decide treatment"
Solutionخصائص محددة للحل. بتنقسم لـ Functional وNon-functional"Calculate total charges including delivery and taxes"
Transitionقدرات مؤقتة لنقل المؤسسة من الوضع الحالي (as-is) للمستقبلي (to-be). بتتعلق بتحويل البيانات والتدريب واستمرارية العمل. ما محتاجة لما النظام يدخل production"Sales personnel must attend a 2-day program قبل استخدام النظام" و"البيانات القديمة تبقى في النظامين لنهاية الربع الأول"
طريقة تفرّق بيهااسأل: "ليه؟" ← Business. "منو محتاج شنو؟" ← Stakeholder. "النظام لازم يعمل/يكون شنو؟" ← Solution. "كيف ننتقل من القديم للجديد؟" ← Transition.

Functional مقابل Non-functional

FunctionalNon-functional (NFR)
خدمات بيقدمها النظام وكيف يتفاعل مع مدخلات معينة. ممكن تذكر كمان ما لا يجب أن يفعلهقيود على الخدمات: زمن، عملية التطوير، معايير. غالباً بتنطبق على النظام كله مش على feature واحد

مثال نظام Mentcare (من الشرائح):

  • "المستخدم يقدر يبحث في قوائم المواعيد لكل العيادات."
  • "النظام يولد كل يوم لكل عيادة قائمة بالمرضى المتوقع حضورهم."
  • "كل موظف يتعرف عليه برقم موظف من 8 أرقام."

مشكلة الغموض (Imprecision)

لو المتطلب ما واضح، المطور والمستخدم بيفهموه بشكلين مختلفين. مثال كلمة "search": المستخدم يقصد البحث عن اسم مريض في كل العيادات، والمطور يفهمها بحث داخل عيادة واحدة يختارها المستخدم الأول. النتيجة نظام غير مطلوب.

لذلك المتطلبات لازم تكون 3Cs: Clear (واضحة)، Complete (كاملة)، Consistent (متسقة بدون تناقض). عملياً صعب تحققها كلها بسبب التعقيد.

Functional Decomposition وWBS

تفكيك نظام معقد لأجزاء أبسط تحلل كل جزء على حدة، والناتج رسم اسمه Work Breakdown Structure (WBS). التسلسل:

High-level Function  ->  Subfunction  ->  Process  ->  Activity

نفكك لحد ما الجزء ما يتفكك أكتر. مثال من عندي مثال توضيحي:

Manage Orders (High-level function)
 ├─ Place Order (Subfunction)
 │    ├─ Validate Cart (Process)
 │    └─ Process Payment (Process)
 │         └─ Charge credit card (Activity)
 └─ Track Order (Subfunction)

Non-functional Requirements بالتفصيل

بتحدد خصائص وقيود مثل الاعتمادية (reliability)، زمن الاستجابة، التخزين، قدرات الـ I/O. مهمة زي الـ functional: لو ما اتحققت ممكن النظام يبقى ما يفيد (نظام صح لكن بياخد دقيقة لكل نقرة ما حد يستخدمه). وبتأثر في معمارية النظام كله.

Goal مقابل Verifiable NFR

Goal (هدف عام، ما يتختبر)Verifiable NFR (قابل للاختبار بقياس)
"النظام سهل الاستخدام للطاقم الطبي ويقلل أخطاء المستخدم""الطاقم يقدر يستخدم كل الوظائف بعد 4 ساعات تدريب، ومتوسط الأخطاء لا يتعدى 2 في الساعة"

القاعدة: لازم يكون في رقم تقدر تختبره. أي كلمة زي "fast" و"easy" و"reasonable" و"secure" لوحدها = goal غامض.

تصنيف الـ NFR (ثلاثة)

FURPS وFURPS+

طريقة لتصنيف الـ NFR. الحروف:

  • Functionality: الوظائف.
  • Usability: الواجهة، المساعدة، التوثيق.
  • Reliability: اعتمادية النظام وخطر انهياره.
  • Performance: قياس الحمل مثل throughput وزمن الاستجابة.
  • Supportability: التركيب والإعداد والمراقبة والصيانة.

الـ "+" بتضيف: Design constraints (قيود على الـ hardware والـ software)، Implementation (لغات وأدوات)، Interface (التفاعل بين الأنظمة)، Physical (حجم، وزن، استهلاك كهرباء، ظروف التشغيل).

Perfect Technology

القاعدةتخيل إن التقنية مثالية (سرعة لا نهائية، ما في أعطال). لو المتطلب لسه مطلوب حتى مع تقنية مثالية ← functional. لو اختفت الحاجة ليه بسبب التقنية المثالية ← non-functional.

مثال من عندي توضيحي: "النظام يتحقق من باسورد المستخدم" سيظل مطلوباً حتى مع تقنية مثالية ← functional. "الباسورد يتحقق في أقل من ثانية" ما نحتاجه مع تقنية مثالية (سرعتها لانهائية) ← non-functional.

الـ Mind map أداة بتساعد تنظم الأفكار حول الموضوع المركزي.

إدارة تعاون الـ Stakeholders

  • Stakeholder lists: قائمة بيهم.
  • Stakeholder maps: مثل Stakeholder Matrix: بتقابل مستوى influence (التأثير) بمستوى impact (التأثر).
  • Persona: شخصية خيالية تمثل فئة مستخدمين، بخصائص نموذجية وقصة قصيرة (مثال الشرائح: Bob مسؤول نظم في IBM بنيويورك، وFritz أب عمره 50 لسباح ألماني).
  • Proto-persona: persona مبنية على معلومات محدودة، بتتعمل كتمرين جماعي للفريق. أقل دقة من persona مبنية على دراسات مستخدمين، لكنها أفضل من لا شيء.

تمارين الشرائح (E-commerce) مع الحل

النص: نظام تسوق يتيح تصفح الكتالوج، اختيار الأصناف ووضعها في سلة، الدفع (credit card وشيكات شخصية وحوالات)، طرق شحن (ground وsecond business day وnext business day)، ولوحة admin لإضافة المنتجات وإدارة حسابات العملاء والمخزون. المطلوب: معاملات دفع آمنة، الاتصال بالعملاء بالإيميل، الالتزام بالقوانين المحلية والدولية ومعيار الشركة STD0945، العميل يحتاج web browser وذاكرة معقولة، زمن استجابة سريع، تحمل الأعطال الشائعة.

استخرج الـ Functional requirements
  • تصفح الكتالوج واختيار الأصناف ووضعها في e-cart.
  • الدفع بـ credit card أو personal check أو money order.
  • اختيار طريقة الشحن (ground / second business day / next business day).
  • Admin: إضافة منتجات، إدارة حسابات العملاء، إدارة المخزون.
  • التواصل مع العملاء بالإيميل.
استخرج الـ Non-functional requirements (وحدد الغامض)
  • معاملات دفع آمنة: غامض (security) ← حوّله لمقياس مثل "تشفير كل بيانات البطاقات بـ TLS".
  • الالتزام بالقوانين المحلية والدولية: External.
  • الالتزام بمعيار STD0945: Organisational.
  • client side: web browser وذاكرة معقولة: constraint، وكلمة "reasonable" غامضة.
  • زمن استجابة سريع: غامض ← "الصفحة تحمل في أقل من 2 ثانية لـ 95% من الطلبات" مثال مني.
  • تحمل الأعطال الشائعة: غامض (reliability) ← حدده بـ MTTF أو availability 99.9%.

تمرين Hospital MS

الجمل في نص الشريحة بالترتيب: (1) النظام يحتفظ بمعلومات الأطباء والمرضى والزيارات والوصفات. (2) الدكتور يزور المرضى ويفحصهم ويضيف تشخيصات ويسجل الأعراض ويصف الأدوية ويجدول الإجراءات ويبلغ عن الحالة ثم يخرج المريض. (3) النظام يحتفظ بمعلومات الأعراض والتشخيص والأدوية. (4) المريض يسجل نفسه ويلغي التسجيل ويؤكد الإجراء الطبي ويملأ طلب الخروج. (5) الدكتور يطلع على تاريخ المريض. (6) حالة المريض: hospitalized, intensive care, away, discharged.

تنبيهأنا اعتمدت الترقيم ده من ترتيب الجمل. ما متأكد إن الدكتورة تقصد نفس الترقيم، فراجع الشريحة. الفكرة في الحلول واحدة حتى لو الرقم اختلف.
أعد كتابة المتطلب 3 كـ stakeholder requirement
"As a doctor, I need to view a patient's symptoms, diagnosis and prescribed drugs so that I can make accurate treatment decisions."
أعد كتابة المتطلب 4 كـ non-functional requirement
"A patient shall be able to complete self-registration in under 3 minutes, and each registration screen shall respond within 2 seconds." (قابل للقياس)
اقترح transition requirement
"All existing paper patient records shall be migrated into the new system before go-live." أو "Doctors and nurses must attend a 1-day training before using the system."
أي متطلب هو business requirement؟
الأول (الهدف العام): النظام يحتفظ بمعلومات الأطباء والمرضى والزيارات والوصفات، لأنه بيجاوب "لماذا" على مستوى المؤسسة.
اقترح personas
(1) د. هالة، 45 سنة، استشارية باطنة، وقتها ضيق وتحتاج وصولاً سريعاً لتاريخ المريض. (2) أ. عمر، 62 سنة، مريض جديد قليل الخبرة بالتقنية ويحتاج واجهة تسجيل بسيطة.

أسئلة تدريب

الفرق بين Business وStakeholder وSolution وTransition requirements؟
Business: لماذا (أهداف عليا). Stakeholder: ماذا يحتاج stakeholder (الجسر). Solution: خصائص الحل (functional وNFR). Transition: مؤقتة لنقل النظام من as-is إلى to-be.
ليه "النظام يجب أن يكون سريعاً" متطلب ضعيف؟
لأنه goal غامض ما يتختبر. لازم يتحول لقياس مثل "زمن الاستجابة أقل من 2 ثانية لـ 95% من الطلبات".
اشرح FURPS+
F وظائف، U usability، R reliability، P performance، S supportability. والـ + تضيف design constraints وimplementation وinterface وphysical.

Lab 3: حل الـ Conflicts، حذف Branch، Rebase، Stash

Case study: ليه بيحصل conflict؟

الـ developers على master لقوا إن الـ business يحتاج my_sum() تاخد 3 أرقام بدل اتنين، فغيروها وعملوا commit. وفي نفس الوقت الـ developers على فرع math-feature لقوا إن الاسم my_sum مش احترافي فغيروه لـ sum(). الاتنين عدلوا نفس السطور. لما ندمج، Git ما يعرف أي تغيير يحتفظ بيه، فيتوقف ويقول لك "حل الـ conflict بنفسك".

        A  (master: my_sum بـ 3 parameters)
       /
base --+
       \
        B  (math-feature: الاسم بقى sum)

متى بالظبط يحصل conflict؟

تذكير بقاعدة لاب 2الـ 3-way merge بينظر لثلاثة commits: base وآخر commit في كل فرع. القاعدة: change vs no-change → the change wins. لو الفرعين عدلوا نفس السطور بشكل مختلف → conflict.

في مثال الشرائح فيه مكانين متعارضين: تعريف الدالة واستدعاؤها، وأجزاء ثانية في الملف عدلها فرع واحد بس (دي اندمجت تلقائياً).

شكل الملف أثناء الـ conflict

<<<<<<< HEAD
  (نسخة الفرع الحالي)
=======
  (نسخة الفرع المدموج)
>>>>>>> اسم-الفرع-أو-الـ-commit

شغلك: تفتح الملف، وتختار الصح (أو تدمج الاتنين)، وتمسح علامات <<<<<<< و======= و>>>>>>> بالكامل.

في مثال المحاضرة الحل كان الاحتفاظ بالتغييرين: الاسم الجديد مع الـ 3 parameters:

int sum(int a, int b, int c)      // الاستدعاء كذلك: sum(2, 4, 6);
إنهاء الـ mergeلتعلن إن الـ conflict اتحل: stage ثم commit للملفات المتعارضة.
git add file.cpp
git commit -m "resolve conflict"

حذف Branch

بعد ما دالة sum انضافت لـ master بنجاح، ما في حاجة للفرع math-feature.

git branch -d <name>    # آمن: يرفض لو فيه تغييرات لم تُدمج
git branch -D <name>    # إجباري: يحذف حتى لو غير مدموج (يضيع الـ commits)
  • ما تقدر تحذف الفرع الحالي (اللي HEAD عليه).
  • سؤال الشرائح: حذف math-feature بـ -d هل يعطي تحذير؟ لا، لأن تغييراته اتدمجت في master.
  • حتى بعد حذف الفرع، الـ git log بيفضل يبين تاريخ الدمج كامل.
توضيح منيالشريحة بتقول "كل الـ commits على الفرع بتتجمع في commit واحد على الفرع الحالي". الأدق إن التغييرات بتدخل عبر merge commit واحد بأبوين، لكن الـ commits الفردية بتفضل في التاريخ (وده سبب إن الـ log بيحتفظ بالدمج حتى بعد حذف الفرع).

Rebase: تاريخ نظيف

لو في ناس كتيرة بتشتغل على فروع وبتدمج، الـ log graph بيبقى زي الشبكة ويصعب تتبعه. git rebase بيحل المشكلة.

الفكرة: يأخذ commits فرعك الحالي ويعيد تطبيقها فوق رأس الفرع الأساسي (بينشئ نسخ جديدة بـ hash جديد). النتيجة تاريخ خطي.

الـ case study (Black Friday): الـ developers عملوا فرع discounts للعروض الجديدة وعدلوا commit، وعلى master نظفوا الملف بحذف أسطر زيادة. لو عملنا git merge الآن بيبقى 3-way (الفرعان تباعدا) والتاريخ يصعب قراءته.

قبل:                       بعد rebase:

C0 --- M1 (master)         C0 --- M1 --- F1' (discounts)
  \                                       ^ master عند M1 (ما اتحرك)
   F1 (discounts)

F1' هي نفس تغييرات F1 لكن commit جديد (hash مختلف) فوق M1.

الخطوات بالترتيب:

git checkout <feature-branch>
git rebase <base-branch>     # لو conflict: حله ثم
git rebase --continue
git checkout <base-branch>
git merge <feature-branch>   # الآن fast-forward لأن فيه direct path
سؤال الشرائح: أي branch pointer اتحرك بعد الـ rebase؟فرع الـ feature هو اللي اتحرك (ونُسخت commits بتاعته). الـ base ما اتحرك لسه، ولذلك محتاجين الخطوة الأخيرة (checkout base ثم merge feature) وهي تبقى fast-forward.

Git Stash

القصة: سارة مبرمجة في منتصف feature (دالة حساب خصم في صفحة السلة). مدير الفريق يرسل: "عاجل! bug حرج في الـ checkout على الـ main". تغييراتها ما جاهزة للـ commit، وهي محتاجة تنتقل لـ main بسرعة بدون ما تفقد شغلها.

Stash: يحفظ تغييراتك المحلية مؤقتاً بدون commit ويرجّع الـ working directory نظيف.

git stash          # يحفظ التغييرات ويُنظف المجلد
git stash list     # قائمة الـ stashes المحفوظة
git stash apply    # يرجّع آخر stash ويبقيه في القائمة (يمكن تطبيقه تاني)
git stash pop      # يرجّع آخر stash ويحذفه من القائمة
git stash drop     # يحذف stash بدون تطبيقه

حل مشكلة سارة (6 خطوات):

  1. git stash (الـ working directory صار نظيف).
  2. git checkout main.
  3. أصلح الـ bug، commit، push.
  4. git checkout feature-branch.
  5. git stash apply (أو pop).
  6. كمّل شغلها كأن شيء ما حصل.

الخطوة 12: git rebase master بيقول Could not apply 264f4b3... dev edit والملف يصير:

#include <iostream>
using namespace std;
int main(){
  cout << "hello" << endl;
<<<<<<< HEAD
  cout << "git is fun edited by master" << endl;
=======
  cout << "git is fun edited by dev" << endl;
>>>>>>> 264f4b3 (dev edit)
}
تفصيلة مهمة في الـ rebaseأثناء الـ rebase، الجزء اللي تحت HEAD هو نسخة master (الفرع اللي تعمل rebase عليه)، والجزء الثاني هو commit بتاعك من dev. ده معكوس شوية عن الـ merge العادي، وناس كتيرة بتتلخبط فيه.

حل الـ conflict: اختر النسخة اللي تريدها (أو اكتب نسخة تجمع الاتنين) وامسح علامات الـ conflict. بعدين:

git add main.cpp
git rebase --continue      # (مو git commit!)

طلع: Successfully rebased and updated refs/heads/dev. والـ graph بعدها خطي:

* aa968ce (HEAD -> dev) dev edit
* 8f13a1b (master) master edit
* 015f0b7 main file

الخطوة 13: على master:

git checkout master
git merge dev
Updating 8f13a1b..aa968ce
Fast-forward
ليه fast-forward؟لأن الـ rebase جعل dev مبنياً مباشرة فوق رأس master، فبقى في مسار مباشر وGit بس يحرك مؤشر master. هذا هو السؤال في الشريحة: "What's the type of merge?"

معلومة عامة خارج الشرائح: لو تراجعت أثناء rebase مليء بالتعارضات، git rebase --abort بيرجعك لحالتك قبل الـ rebase.

أسئلة تدريب

متى يحدث merge conflict؟
لما يعدل فرعان نفس السطور في نفس الملف بشكل مختلف. لو غيّر فرع واحد بس الجزء، تغييره يكسب تلقائياً.
كيف تعلن لـ Git إن الـ conflict اتحل في merge عادي؟
تعدل الملف وتمسح العلامات، ثم stage وcommit للملف.
الفرق بين -d و-D؟
-d آمن ويرفض حذف فرع فيه تغييرات لم تُدمج. -D إجباري ويحذف حتى مع تغييرات غير مدمجة (تضيع نهائياً). ولا يمكن حذف الفرع الحالي.
ماذا يفعل rebase؟ وليه الـ merge بعده fast-forward؟
ينقل commits فرعك فوق رأس الـ base بنسخ جديدة (hash جديد) فيصير التاريخ خطياً. بعده فرع الـ feature مبني مباشرة فوق الـ base، فيوجد direct path ويصير الـ merge fast-forward.
متى لا تستخدم rebase؟
لما الفرع يكون مدفوعاً (pushed) أو مشتركاً مع آخرين، لأنه يغير commit IDs ويكسر نسخهم.
الفرق بين stash apply وstash pop؟
apply يرجّع التغييرات ويترك الـ stash في القائمة. pop يرجّعها ويحذف الـ stash من القائمة.
أنت في منتصف feature وجاك bug عاجل، شنو تعمل؟
git stash ← git checkout main ← أصلح وcommit وpush ← git checkout feature ← git stash apply ← كمّل.
